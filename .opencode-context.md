## Architecture Decisions
- SQLite is for local demo only; production requires a managed concurrent-write database and real payment integration.
- Product ratings are derived from verified product_reviews, unique per order item; products no longer persist editable/demo rating values.
- Completed reviews survive product deletion through nullable product_id, while order item review snapshots remain visible.
- Product recency is derived from immutable created_at with id as deterministic cursor tie-breaker; no mutable sequence/counter column is maintained.
- Any SQLite migration that rebuilds products must explicitly restore product_search synchronization triggers because SQLite table rebuilds drop those triggers.
- Rental product stock cannot fall below peak concurrent reserved quantity; disjoint reservations do not consume simultaneous capacity.
- Rental products with active reservations cannot change to sale products. Deactivation remains allowed to stop new bookings.
- Product mutations lock the product row before checking active rental capacity and writing stock or type changes.
- Checkout rejects products owned by the buyer after locking all requested product rows and before mutating stock or reservations.
- Self-checkout is a 409 domain conflict; mixed baskets roll back atomically and expose one actionable message to the existing checkout UI.
- Review eligibility is defined by OrderItem::isFulfilledForReview and shared by API mutation and order payload projection.
- Sale items require completed fulfillment; rental items additionally require a completed reservation. Cancelled rentals are never reviewable.
- Fulfillment transition projection and mutation share OrderFulfillment::availableTransitions and canTransitionTo.
- Ready rental fulfillment offers completion only when every reserved rental has reached its inclusive end date.
- Authenticated routes use Laravel auth.session so sessions are bound to the current password hash.
- Password rotation synchronizes the guard user to the locked updated row; the rotating session stays active while stale sessions receive JSON 401.
- Guest redirects resolve to null because authentication is handled by JSON APIs and modal UI, not a named login route.
- Login and registration seed password_hash_web with the SessionGuard HMAC, closing the cold-session gap before the first auth.session request.
- GET /api/me uses auth.session without auth: guests retain 200 {user:null}; stale password-bound sessions receive JSON 401.
- Review bodies are optional free text capped at ProductReview::MAX_BODY_LENGTH (500); blank input normalizes to null instead of an empty string.
- The public review feed GET /api/products/{product}/reviews requires no authentication and serves active listings only; inactive or deleted products return 404 while stored reviews survive.
- Public reviewer identity is masked to given name plus family-name initial by ProductReview::reviewerLabel; buyer email and account id are never exposed.
- Rating distribution is one grouped count query over product_reviews, zero-filled for every star bucket so the UI never issues five separate counts.
- product_reviews cursor pagination uses reviews_product_cursor_index (product_id, created_at, id) so the feed avoids temp b-tree sorting.
- product_reviews.seller_id is snapshotted from the locked product at review creation, so a seller keeps inbox and reply access after the listing is deleted (product_id nulls out, seller_id survives).
- Seller reply ownership is re-checked against the lockForUpdate row inside the transaction; a stale seller_id from a concurrent listing transfer cannot win the write.
- Replies never mutate rating or buyer body; DELETE clears seller_reply and seller_replied_at together.
- Seller inbox reuses the masked reviewerLabel, so a seller sees ratings and text but never a buyer email or full name.
- Notifications live in user_notifications, deliberately NOT Laravel's notifications table, because User uses the Notifiable trait whose notifications() relation expects the framework morph/uuid schema.
- NotificationRecorder is the single write path: insertOrIgnore against a unique event_key makes fan-out idempotent under transaction retries and same-state mutation replays.
- The recorder drops any row whose recipient_id equals actor_id, so a user is never notified about their own action.
- Fan-out runs inside the existing mutation transaction, so a rolled-back checkout or transition leaves no orphan notification.
- Review replies notify the buyer only when a reply first appears; the previous value is read from the locked row, so later edits stay silent.
- Fulfillment message read markers store the last-read message id, NOT a timestamp: created_at has second precision, so "created_at > marker" silently misses messages written in the same second. Ids are monotonic and exact.
- Message thread participation is resolved per fulfillment (owning seller plus parent-order buyer), not per URL prefix, so one shared route pair serves both parties and a rival seller on the same order still gets 403.
- fulfillment_messages is append-only like order_activities: a conversation is dispute evidence, so neither side may rewrite it.
- sender_role is snapshotted on each message so the thread stays readable after a sender account is deleted.
- Cancelled fulfillments reject new messages with 409 but keep full history readable.
- List endpoints use scopeWithUnreadMessageCount (one correlated subquery) instead of per-row unreadCountFor, keeping paginated payloads page-size invariant.
- RentalCapacity is the single capacity calculation for availability, checkout, and stock/type mutation guards; it computes the joint daily peak of reservations plus blocks. Never sum allocations per range: reservations on different days do not consume capacity simultaneously.
- rental_blocks store inclusive dates, quantity, a private note, and cancelled_at; cancellation is idempotent and cancelled or past blocks hold no future capacity.
- Block notes and ids never leave the owner-only endpoint; public availability exposes only reserved/blocked/unavailable/available quantities.

## Conventions
- Guest assertions inside a test that already called actingAs MUST reset first with $this->flushSession()->actingAsGuest(); otherwise the authenticated session leaks and 401 assertions fail.
- hub readiness by port alone is unreliable for php artisan serve: another project may already hold the port. Match the log line "Server running on \[http://127.0.0.1:<port>\]" instead.
- order_fulfillments.seller_name is a product snapshot (products.seller, faker-generated in tests), NOT the seller account name. Match fulfillments on seller_id.
