## Architecture Decisions
- SQLite is for local demo only; production requires a managed concurrent-write database and real payment integration.
- Product ratings are derived from verified product_reviews, unique per order item; products no longer persist editable/demo rating values.
- Completed reviews survive product deletion through nullable product_id, while order item review snapshots remain visible.
- Product recency is derived from immutable created_at with id as deterministic cursor tie-breaker; no mutable sequence/counter column is maintained.
- Any SQLite migration that rebuilds products must explicitly restore product_search synchronization triggers because SQLite table rebuilds drop those triggers.
- Rental product stock cannot fall below peak concurrent reserved quantity; disjoint reservations do not consume simultaneous capacity.
- Rental products with active reservations cannot change to sale products. Deactivation remains allowed to stop new bookings.
- Product mutations lock the product row before checking active rental capacity and writing stock or type changes.
- Checkout rejects products owned by the buyer after locking all requested product rows and before mutating stock or reservations.
- Self-checkout is a 409 domain conflict; mixed baskets roll back atomically and expose one actionable message to the existing checkout UI.
- Review eligibility is defined by OrderItem::isFulfilledForReview and shared by API mutation and order payload projection.
- Sale items require completed fulfillment; rental items additionally require a completed reservation. Cancelled rentals are never reviewable.
- Fulfillment transition projection and mutation share OrderFulfillment::availableTransitions and canTransitionTo.
- Ready rental fulfillment offers completion only when every reserved rental has reached its inclusive end date.
- Authenticated routes use Laravel auth.session so sessions are bound to the current password hash.
- Password rotation synchronizes the guard user to the locked updated row; the rotating session stays active while stale sessions receive JSON 401.
- Guest redirects resolve to null because authentication is handled by JSON APIs and modal UI, not a named login route.
- Login and registration seed password_hash_web with the SessionGuard HMAC, closing the cold-session gap before the first auth.session request.
- GET /api/me uses auth.session without auth: guests retain 200 {user:null}; stale password-bound sessions receive JSON 401.
